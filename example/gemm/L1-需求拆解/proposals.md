# 需求拆解 — GEMM 本机 CPU 加速

## 原始需求

在本机 CPU 上实现一个矩阵乘法（GEMM）加速库，作为 VINW 流程的第二个实战工程，用于验证 VINW 在非 Python、非自举场景下的可用性。

## 分解结果

| 编号 | 子需求 | 优先级 | 约束 / 验收标准 |
|------|--------|--------|----------------|
| R1 | 公共 C 接口：`gemm(M, N, K, A, B, C)`，行主序 float32，`C = alpha*A@B + beta*C`（alpha=1,beta=0 起步） | P0 | 头文件 `gemm.h`，ABI 稳定，无第三方运行时依赖 |
| R2 | 正确性：与朴素参考实现逐元素对比 | P0 | 随机矩阵 + 边界尺寸（1×1、奇数、非方阵）；`max|diff| <= 1e-3 * |ref|` |
| R3 | 单线程性能：分块 + 打包 + 微内核 | P0 | **相对真·朴素 ijk 实现 ≥ 8×**（descent-3 修订：见下方「性能基线口径」） |
| R4 | 多线程性能：pthreads 按行块并行 | P0 | 8 核上相对单线程 ≥ 4×（实测 4.34× 已达标） |
| R5 | 性能基准工具：尺寸扫描 + 线程数扫描 | P0 | 输出 GFLOPS 表格；对比 Accelerate cblas_sgemm 作为上界参考 |
| R6 | 可移植：arm64（NEON）与 x86_64（AVX2）均可编译运行 | P1 | 依赖编译器自动向量化；不写死 intrinsic |
| R7 | 构建：`make` 一条命令产出库 + 测试 + 基准 | P1 | Apple clang 21 / arm64 实测通过 |

## 性能基线口径（descent-3 修订，cfm-20261114-072455-003 用户裁定）

原 R3/验收条款写「相对 naive ikj ≥ 8×」。descent-3 实测（Apple M3，4P+4E）：

| 基线 / 参照 | 单线程 GFLOPS | 性质 |
|------|---:|------|
| 真·朴素 ijk | 3.56 | 内层步长 N，**验收门槛基线** |
| ikj（原 bench 基线） | 23.64 | 缓存友好 + 全向量化，**性能上限参照** |
| blocked（本项目 1T） | 25.14 | 已达单核峰值 65% |
| blocked（本项目 8T） | 109.19 | 4.34× 扩展 |
| Accelerate cblas | 1597 | 走 AMX 协处理器，纯 C 不可比，**仅上界参考** |
| 显式 SIMD FMA 实测单核峰值 | 38.5 | 8 独立 v4 累加器的理论可达 |

**为什么改口径**：8×23.64 = 189 GFLOPS ≈ 整机估算峰值（4P×38.5 + 4E 约 20 ≈ 234）的 81%。
不是物理不可达，而是要求纯 C+编译器自动向量化在 1024³ 上达到整机 81% 效率——
远超本项目「依赖编译器自动向量化、不写 intrinsic」的技术选型（R6）。
相对一个**已经缓存优化、已吃到 61% 峰值**的基线再要 8×，实质是要求 81% 整机效率，
与 R6 的自限冲突。

**裁定结果（用户选择 both-baselines）**：

| 指标 | 门槛 | descent-3 实测 | 状态 |
|------|------|---------------|------|
| 单线程 vs 真·朴素 ijk | ≥ 8×（需 ≥28.5 GFLOPS） | 7.06×（25.14） | ❌ 差 ~13%，需优化微内核 |
| 8 线程 vs 真·朴素 ijk | ≥ 8× | 30.6× ✅ | ✅ |
| 8 线程 vs 单线程（扩展性） | ≥ 4× | 4.34× ✅ | ✅ |
| ikj / Accelerate | 参照展示，不作门槛 | 3.9× / 14.6× | 参考 |

若 ST 优化后仍达不到 8×（28.5 GFLOPS = 单核峰值 74%），则按 force 记录并以实际值验收，
不得修改门槛数字来"通过"。

## 非目标（明确排除）

- 不做 FP16 / BF16 / INT8 量化
- 不做 GPU（Metal / CUDA）
- 不做 batched GEMM
- 不做转置 / Strided 变体（仅 NN 布局）

## 关键问题域

| 编号 | 问题域 | 说明 |
|------|--------|------|
| Q1 | 分块参数 | MC/KC/NC 与 L1/L2 缓存容量的匹配；arm64 与 x86 缓存差异 |
| Q2 | 打包（packing） | 是否打包 A/B，打包收益与额外内存拷贝的权衡 |
| Q3 | 微内核 | 手写 MR×NR 内核 vs 依赖编译器自动向量化 |
| Q4 | 并行策略 | OpenMP 按 M 分块 vs 按 N 分块；线程数超订风险 |
| Q5 | 浮点误差 | 累加顺序变化带来的误差，容差如何界定 |
| Q6 | 基准方法 | 预热、多次取中位数、避免缓存效应失真 |

## 验收方式

1. `make test` 全部用例通过（含边界尺寸）
2. `make bench` 输出表格：naive / blocked-1T / blocked-MT / Accelerate 的 GFLOPS
3. 在 1024×1024×1024 上 **blocked-MT 相对真·朴素 ijk ≥ 8×**（双基线方案，见下）
