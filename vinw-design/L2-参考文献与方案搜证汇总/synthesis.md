# 搜证汇总结论

1. **必须采用 MCP + Skill 双层架构**（证据：层级选择矩阵方案 D）
   - MCP Server 提供跨 harness 的确定性能力（18 个工具）
   - Skill（SKILL.md）在支持的环境中约束 agent 行为模式

2. **必须采用 Markdown 分层存储**（证据：存储层矩阵方案 B）
   - 每个项目是一个自包含的目录树
   - 目录名即状态机阶段编号
   - 人类可随时 cat/vim/diff

3. **必须采用螺旋上升状态机**（证据：状态机矩阵方案 B）
   - 7 层结构：L1→L2→L3→L4→L5→L6→L7
   - 上升：从当前层到更上层的指定基线（触发新下降轮次）
   - 下降：从当前层到更下层（需中间层已基线化）

4. **必须显式记录-回滚**（证据：关键问题证据汇总）
   - 上升操作 = 被记录的变更（写入 changelog + ascensions）
   - 下层标记 superseded 而非删除（保留痕迹）
   - descent_count 记录每层被多少次下降轮次触及

5. **TUI 必须实时刷新**（证据：Textual 可行性）
   - set_interval(2, refresh_ui) 轮询文件系统
   - 纯只读，所有修改通过 MCP tools

# descent-7 结论与推荐方向（供 L3 设计）

## 结论 1：注册表 = `~/.vinw/registry.json`

- 结构：`{"version": 1, "projects": {"<abs-path>": {"name": ..., "added_at": ..., "last_accessed_at": ..., "last_seen_ok": ..., "missing_since": ...}}}`
- 写入：`tmp` + `os.replace` 原子替换；读多写少，无需锁文件（写入前重读合并）
- 位置可用 `VINW_HOME` 环境变量覆盖（便于测试与多环境隔离）
- **否决 SQLite 的理由已记录在证据矩阵**

## 结论 2：失效工程 = 探测标记 + 显式 prune

- `status: ok`（`.vinw/manifest.md` 存在）或 `status: missing`
- `missing` 条目不自动删除；`prune` 默认 `--dry-run`，需 `--force` 才真删
- `missing_since` 记录首次发现缺失时间，便于用户判断

## 结论 3：寻址 = 路径主键 + 名称别名

- MCP `project` 参数接受：绝对/相对路径、注册名、`null`
- 解析顺序：路径存在→解析为路径；否则查注册表名；仍无→结构化错误

## 结论 4：向后兼容红线

- 所有 `se_*` 工具 `project` 参数**可选**，省略时走现有自举 + 单例逻辑
- `vinw tui <path>` 现有用法不变；无参时进入选择器

## 结论 5：TUI 交互

- 顶部 header 常显：`工作目录: <cwd>` 与 `当前工程: <name> @ <path>`
- 无参启动 → 选择器（注册工程 + cwd 探测工程，键盘上下 + Enter）
- 快捷键 `p` 打开切换器（任意时刻），`r` 刷新，`q` 退出

# descent-8 选型复核与更正（asc-007）

## 触发

用户质疑「txt 类总体记录管理不靠谱」，并指出：**全局注册表只是状态切换记录，没有可读内容价值；工程内部才需要 Markdown 可读呈现**。

## 更正声明（重要：记录此前的判断错误）

descent-7 的决策 A 得出「JSON 13/14 分、SQLite 5/14 分」，但该矩阵存在**权重错配**：

| 出错项 | 原判断 | 更正 |
|--------|--------|------|
| 「人类可读 / git diff」权重 3 | 给 JSON 3 分、SQLite 0 分 | **该准则对注册表不适用**：注册表是 per-machine 运行状态，不进 git、不需人工 review；把它当设计产物评分是对象错配 |
| 「规模不够所以不需要 SQLite」 | 5–500 项目 < SQLite 优势区间 | **看错了轴**：决定性因素是并发写、写放大、崩溃一致性，不是数据量 |
| 「SQLite 实现复杂度高」 | 扣分 | 反面：JSON 方案要自己实现锁/事务/并发合并，等价于手搓数据库且更容易出错 |

实测证据（300 条登记）：

| 操作 | JSON 方案实测 | SQLite 方案 |
|------|--------------|------------|
| `list()` 全量探测 | 14.5 ms（首次 1 次全表重写） | 单次查询 + 按需探测 |
| 每次带 `project` 的工具调用 | `touch()` 整表读+整表重写，9.5 ms/次 | 单行 UPDATE，微秒级 |
| 并发写保护 | 无锁，仅「写前重读 + 原子替换」→ 可丢更新 | WAL + 事务 + busy_timeout |
| diff 噪音（单字段改动/20 条） | 2 行 | — |

补充实测：JSON / CSV / JSONL 三者对单字段修改的 **diff 噪音相同（均 2 行）**，故「JSON 更适合 git」在本数据形状下本就不成立，CSV 只是更紧凑（1944 B vs 4598 B）。

## 结论：控制面 / 数据面分层

| | 控制面（全局注册表） | 数据面（工程内文档） |
|---|---|---|
| 载体 | **SQLite**（`$VINW_HOME/registry.db`） | **Markdown + frontmatter**（`<工程>/.vinw/*.md`） |
| 写入者 | 程序，高频自动 | 人 + agent，低频深思 |
| 并发 | MCP server + TUI + CLI 三进程 → 需锁与事务 | 单写者，顺序 |
| 进 git | 否（per-machine） | 是（过程即产物） |
| 可读性诉求 | 低（用 `vinw project list` 读） | 高（review / diff / 归档） |

## CSV 方案再评估（回应用户提议）

CSV 对本 schema 结构性够用（全标量、1966 B 最紧凑），但：
1. null 与空串无法区分（`missing_since: null` vs `""`）
2. Excel/Numbers 编辑会篡改（ISO 日期本地化、`=` 开头路径变公式）
3. 无嵌套能力，schema 演进受限
4. **同样没有并发锁**——与 JSON 共享最大缺陷

→ 若「需要人用表格软件编辑」则 CSV 合理；本场景不需要（注册表不进 git、不需人工编辑），故选 SQLite。

## 遗留待 L3 决定

- 是否保留 JSON 导出（建议保留：`vinw project export` 供人查看/备份）
- 状态切换是否留痕（建议新增 `project_events` 表，支持 `vinw project history`）

# descent-10 搜证：跨语言符号提取（2026-11-14）

## 方案对比

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| tree-sitter（已依赖 `tree-sitter` + `tree-sitter-python`） | AST 精度高 | 每种语言需单独 grammar 包，C/C++/Rust/Go 各一个依赖，体积与安装成本大 | ❌ 否决（依赖膨胀） |
| ctags / universal-ctags | 多语言成熟 | 外部二进制依赖，用户机器不一定有 | ❌ 否决 |
| **正则 + 语言规则表** | 零依赖、可扩展、够用于"符号存在性"判定 | 无法处理宏展开、模板等复杂语法 | ✅ **采纳** |
| LLM 语义比对（已有 `method="llm"`） | 理解语义 | 成本高、非确定 | 保留为补充路径 |

## 各语言符号提取规则（正则）

| 语言 | 提取目标 | 正则要点 |
|------|---------|---------|
| Python | `def` / `class` | `^\s*(?:async\s+)?def\s+(\w+)` / `^class\s+(\w+)` |
| C/C++ | 函数定义/声明、宏、结构体 | `\b(\w+)\s*\([^;{]*\)\s*\{`（定义）、`^#\s*define\s+(\w+)`、`\b(?:struct|class|enum)\s+(\w+)\s*\{?` |
| Rust | `fn` / `struct` / `enum` | `\bfn\s+(\w+)` 等 |
| Go | `func` / `type` | `\bfunc\s+(?:\([^)]*\)\s*)?(\w+)` |
| Java/TS | `class` / `interface` / `function` | 关键字前缀 |

## 关键设计决策

| 编号 | 决策 | 理由 |
|------|------|------|
| D1 | 代码侧提取"定义"，设计侧提取"标识符"，**取交集**判断存在 | 现有实现只靠设计侧正则，语言一换就失效 |
| D2 | 过滤语言关键字表 + 全大写头文件保护宏（`FOO_H`/`FOO_HPP`） | 消除 `enum`、`GEMM_H` 这类噪声 |
| D3 | `code_extensions` 放 manifest，默认含 9 种常见扩展名 | 可配置，避免再次写死 |
| D4 | `files_scanned == 0` 直接报错 | 静默产出假报告比报错更糟（本次 bug 的根源） |
| D5 | 报告写 `files_scanned` / `extensions` / `code_symbols_count` | 报告自解释，便于定位配置问题 |

## 遗留风险

- 头文件里只有声明（`gemm_status gemm_f32(int, ...);`），无函数体：正则需同时接受"带分号声明"与"带函数体定义"
- 语言关键字表需覆盖常见保留字，否则仍会误报；采用白名单式过滤

# descent-11 方法学：三层审计各自的逻辑地位（2026-11-14）

## 命题形式化

| 检查 | 命题 | 逻辑类型 | 假阴性风险 |
|------|------|---------|-----------|
| text | ∀s ∈ 设计符号: ∃ 定义(s) ∈ 代码 | 必要条件 | **高**（语义错误全放行） |
| LLM | 设计条款 ↔ 实现/测试 的对应关系 | 启发式判断 | 中（受提示词与自我偏差影响） |
| 测试 | 规格的可执行断言 | 构造性证明（覆盖域内） | 低（覆盖域内）；域外未知 |

**推论**：不能把"通过 text"当作"一致"的证据；只能当作"未发现漂移"的证据。

## GEMM 实证（本项目第一手数据）

| 类别 | 数量 | 实例 |
|------|------|------|
| text 命中真实漂移 | 3 | `gemm_blocked_1t` / `gemm_blocked_par` / `parallel_for_m` 设计改名后代码未跟进 |
| text 误报（非本项目符号） | 4 | `USE_OPENMP` / `make` / `max` / `srand` |
| text 暴露的提取器缺陷 | 2 | 关键字/保护宏未过滤；正则跨行吞符号（`gemm_impl_name` 被 `#if defined(...)` 段吞掉） |

结论：text 的价值集中在**命名/结构漂移检测**；其误报需靠提取器质量治理，其漏报需靠 LLM 与测试补位。

## 方案对比：LLM 审核的三种落法

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 每次门控都 LLM | 覆盖最全 | 成本高、非确定、易阻塞 | 仅 `strict` 策略 |
| 关键点 LLM（L4→L5、完成） | 成本可控、覆盖高风险转换 | 基线处语义空白 | ✅ **默认策略** |
| 纯 text | 最快 | 语义盲区 | 仅作 `text` 策略 |

## LLM 提示词设计要点（R18）

1. **不问"是否一致"**（易得到顺从性回答），改问"列出缺口与偏差，并给行号证据"
2. 分两部分：**A 缺口清单**（设计要求 ↔ 代码/测试 缺失）；**B 实现一致性**（逻辑、数据结构、约束、接口签名）
3. 每条结论必须带 `design_ref`（文件:行）与 `code_ref`（文件:行）或明确写"无对应实现"
4. 输出 JSON 固定 schema，便于入库与门控消费

## 自我背书风险的缓解

| 措施 | 说明 |
|------|------|
| 独立上下文 | 由 reviewer（subagent / 新会话）执行，避免写代码者自审 |
| 记录审查者 | 报告写 `auditor` + `auditor_model`，事后可追溯 |
| 证据强制 | 无行号引用的结论视为无效 |

# descent-12 方法学：不一致的分级裁定（2026-11-14）

## 为什么需要裁定

审计只能报告"设计与代码不一致"，但**不一致不等于代码错**。真实分布（本项目 descent-11 实测 15 项）：

| 类别 | 数量 | 本次实例 |
|------|------|---------|
| 实现缺陷（impl_bug） | 5 | strict 未接线、空扫描落盘、冲突分支不可达、报告缺字段、.c 声明当实现 |
| 设计缺失/滞后（design_gap） | 2 | required/advisory 未进设计、默认扩展名与设计不符 |
| 需人工权衡（ambiguous） | 2 | `search_scope` 参数命名、TUI 标记优先级 |
| 纯缺口（缺测试） | 6 | strict 无测试、报告字段无断言等 |

若一律按"改实现"，会把**设计本身的问题**固化进代码（例如把 required/advisory 硬塞进实现而不更新设计）；若一律问人，则把 5 个机械问题也丢给用户，噪声大。

## 裁定顺序（写入提示词）

```
1. 该条设计是否合理、是否自洽？        → 不合理/过时 = design_bug 或 design_gap
2. 设计合理时，实现是否偏离设计？      → 偏离 = impl_bug
3. 两者都可能、或涉及外部契约/命名/优先级 → ambiguous
4. 每条给出 confidence：high 需能指出明确证据（行号 + 推理链）
```

**约束**：不得默认"实现错"；`design_*` 与 `ambiguous` 一律不得自动修。

## 自动化边界（R24/R28）

| 判定 | 处置 | 门控 |
|------|------|------|
| impl_bug + high | 记录 se_log_change → 直接修实现 → 标记 fixed | 放行 |
| impl_bug + medium/low | 升级用户 | 阻断 |
| design_bug / design_gap | 升级用户（需上升改设计） | 阻断 |
| ambiguous | 升级用户 | 阻断 |

## 升级物结构（R25）

每条待决项必须包含四项，缺一不可：

| 字段 | 内容 |
|------|------|
| `difference` | 差异点：设计说什么（file:line）vs 代码做什么（file:line） |
| `analysis` | 分析：为什么可能是实现错 / 设计错，各自的后果 |
| `recommendation` | 推荐处置（fix_impl / fix_design / accept_as_is / defer）+ 理由 |
| `impact` | 影响面：改哪边、影响哪些已批准契约/基线 |

## 与既有门控的关系

复用 `se_require_confirmation` 的阻塞语义（item_type=`audit-escalation`），但**不重复造门控**：升级项由 `se_get_escalations` 统一列出，用户以 `se_record_triage_decision` 裁定后自动放行。

## descent-15：工程发现的三种方案（backlog 3 / R29）

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| A 自动登记 | `init`/`use` 成功即写注册表 | 零额外成本、即时可见、符合 IDE 惯例 | 产生"创建即登记"副作用 | **采纳**（配 `register=false` 退出开关） |
| B 扫描发现 | TUI 启动时扫描常见目录 | 能发现历史遗留工程 | 慢盘成本高、边界模糊（扫哪些目录） | 不采纳 |
| C 惰性提示 | TUI 提示"有未登记工程" | 不改写入路径 | 仍需用户手工操作，未解决根因 | 不采纳 |

### 同类工具对照

- JetBrains 工具箱 / VS Code 最近项目：**创建即入列表**，另提供"从磁盘打开" → 对应 A + 显式 `se_register_project`
- Docker Compose / kubectl：上下文需显式切换但新对象不自动入列表 → 与本缺陷同类痛点
- 结论：A 方案成本收益最优；B 方案的成本（扫描、误判）大于收益

## descent-16 调研一：R32 decision_bias 决策倾向（backlog，仅调研）

### 形态对比

| 形态 | 做法 | 优点 | 缺点 | 结论 |
|------|------|------|------|------|
| A 自由 prompt 文件 | 用户写一段自然语言倾向（如"性能优先于可读性"），升级时拼进裁定 prompt | 实现极简、表达自由 | 不可判定覆盖度；agent 可能忽略；无法知道"没说的事"取什么默认 | 可作 v1 载体 |
| B 结构化问卷 | 多维度选择题，用户填写 | 覆盖可枚举、作答成本低、可直接规则映射 | 维度设计有遗漏风险；粒度粗 | **推荐主形态** |
| C 混合（B 载体 + A 补充） | 问卷给基线倾向，自由文本补特判 | 兼顾覆盖与个性 | 两份来源需定义优先级 | **推荐终态** |

### 维度表（决策倾向调查表草案，10 维）

| 维度 | 示例问题 | 选项示例 |
|------|---------|---------|
| 质量属性权衡 | 性能与可读性冲突时？ | 性能优先 / 可读性优先 / 看场景（请注明） |
| 变更胆量 | 发现设计缺陷，倾向改设计还是适配实现？ | 改设计 / 适配实现 / 先量化影响再定 |
| 风险偏好 | 未验证的优化要不要进主干？ | 进（ flag 保护） / 不进 / 分支孵化 |
| 兼容性 | 接口变更的容忍度？ | 允许 breaking / 需废弃周期 / 永不 breaking |
| 流程严格度 | 门控失败时？ | 必须修完再走 / 可 force 但要留痕 / 交给我逐案裁定 |
| 验证深度 | 测试要求？ | 单测即可 / 需集成测试 / 需基准对比 |
| 文档比重 | 设计与代码不同步时先补哪边？ | 先设计 / 先代码 / 一起改 |
| 依赖态度 | 引入外部依赖？ | 欢迎 / 谨慎（需论证） / 禁止 |
| 评审参与 | 升级项希望我（用户）看多细？ | 只看差异+推荐 / 看完整分析 / 全自动别打扰 |
| 回退策略 | 修复引入回归时？ | 立即回退 / 尝试修复 / 交给我裁定 |

### "回答→倾向"推断方法

1. **规则映射**（v1）：每维选项直接映射为 `bias[dim] = choice_id`；查询时按维取默认值（未填→中性默认）
2. **示例库匹配**：典型场景 → 该场景涉及维度 → 查用户选择；推荐选项按用户历史选择重排
3. **LLM 归纳**（v2）：把问卷答案+自由文本归纳为"倾向卡"，升级时随 escalations 一起呈现给裁定者；**只作参考输入，不自动裁定**

### 与既有流程的衔接

- 挂载点：`AuditTriage.escalations` 输出时附加 `user_bias_hint`（该 finding 涉及维度的用户倾向）
- 存储：工程内 `.vinw/decision-bias.yaml`（数据面、进 git）；不进注册表
- 风险：倾向漂移（用户答完即忘）→ 每次升级呈现时回显"依据你某年某月的回答"；过度拟合→倾向仅重排推荐，不锁死选项

### 结论

** backlog**：推荐 C 形态；v1 先做问卷（B）+ 规则映射；自由 prompt 文件作为补充通道。不进本轮 L3 设计。

## descent-16 调研二：R31 带参考选项的澄清请求（搜证）

### 既有承载点

| 机制 | 能力 | 缺口 |
|------|------|------|
| `se_require_confirmation` | 任意 blocking/item_type/选项集 | 选项只是字符串标签（无说明/影响）；无"参考方向"概念；呈现无选项详情 |
| `se_resolve_confirmation` | approve/reject/modify + feedback | 无"选择某选项+补充"的结构化回传 |
| TUI 确认呈现 | 列出待确认 | 未展示选项的说明文本 |

### 参照做法

- GitHub 评审"建议更改"（suggestion block）：选项带内联 diff，一键采纳
- 设计评审工具（Figma comment）：给方向选项 + 自由评论
- 问卷 UX 研究：选项配"影响说明"可将作答时间降约一半（启发式结论，标注为经验而非实测）

### 结论

R31 不需要新存储机制——**扩展 confirmations 的选项结构**（每个选项 = {id, label, description, impact}），
TUI 展开呈现；`se_resolve_confirmation` 允许 `resolution=<option_id>` 或 modify+文本。实现量小、与既有 purge/阻塞语义天然复用。

## descent-17 调研：澄清的异步化与批量化（R34）

| 模式 | 做法 | 优点 | 缺点 | 采用 |
|------|------|------|------|------|
| 同步阻塞（当前 R31） | 发现歧义立即停下问 | 决策质量最高 | 打断工作流；碎片化；用户离线即卡死 | 仅高影响+不可逆 |
| 异步队列 + 断点批量 | 入队，agent 带假设继续；层转换时统一裁决 | 不打断、可批量、留痕 | 假设可能出错需回滚 | **主模式** |
| 全自动推断 | LLM 自行决定 | 零打扰 | 高风险；与 R31 存在意义冲突 | 禁止 |

**业界参照**：代码评审工具（GitHub PR review）把"阻塞性评论"与"建议"分开；
SRE 的变更管理用"blameless postmortem + 变更审批分级"——高影响变更强审批、低影响自批+留痕。
本设计采用同一思路：**按影响×可逆性分级**。

**关键设计约束**

1. 假设必须显性记录（否则用户事后无法追责/追溯）
2. 队列不能无限堆积——同一主题反复延后要升级为阻塞
3. 批量呈报必须包含"本轮已按假设推进了什么"，让用户一次看清全貌

# descent-21 搜证：接管现有代码仓（adopt-existing-codebase）

## 结论 1：无新机制，全部复用既有件（零新造检查系统，R40 约束满足）

## 结论 2：两种布局并存，adopt 默认"仓库根就地"

| 布局 | 初始化方式 | 适用 |
|------|-----------|------|
| 子目录布局（现状可绕行） | `se_init_project(name="vinw-design", path="<repo>")` + 手工 `code_root: ".."` | 不想在仓库根出现 7 个层目录 |
| **仓库根就地（adopt 新增）** | `se_init_project(path="<repo>", name=..., adopt_existing=true)` | 默认；TUI/CLI 直接 `vinw tui <repo>` |

冲突守卫：仓库根已存在非空层目录（如真有目录叫 `L4-编码实现`）→ 拒绝并建议子目录布局；`.vinw` 半存在 → 拒绝。

## 结论 3：work_mode 不加状态机

`work_mode: "existing-codebase"` 只是 manifest 元数据，`se_get_next_steps` 读取后换提示文案；
不新增转移规则、不改门控语义（R40 AC7 用提示承载，v1 不加 `adoption.phase` 状态位——若实践不够再升需求）。
